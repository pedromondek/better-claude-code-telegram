# 001. Instalação por binário e marketplace do GitHub

> **Versão:** 6 · **Decidido por:** pedromondek
> **Criado em:** 2026-10-24 00:10 · **Atualizado em:** 2026-11-27 01:09
> **Âncoras:** `.claude-plugin/marketplace.json` · `rust/crates/bcct/src/install.rs` (`marketplace_source`, `MARKETPLACE_REPO`) · `rust/crates/bcct/src/self_install.rs` (`Channel`, `Store`) · `rust/crates/bcct/src/update.rs` (`CHECKSUMS_FILE`, `parse_dist_tags`) · `rust/crates/bcct/src/session_start.rs` · `plugins/telegram-hooks/hooks/hooks.json` · `plugins/telegram-hooks/scripts/bcct`

**Decisão:** o usuário instala por `npx @pedromondek/better-claude-code-telegram`, um shim que traz como dependência opcional o binário da plataforma (6 alvos nativos: Linux x64 e arm64 em musl estático, macOS arm64 e x64, Windows x64 e arm64) e roda o setup no terminal. O setup registra o marketplace do GitHub (`MARKETPLACE_REPO`) numa ref fixa, `#stable` na estável e `#v<versão>` numa de teste (`marketplace_source`), e instala os plugins dali, sem clone; a branch `stable` só anda pelo release. O binário de cada versão fica em `bin/versions/<canal>/<versão>/` (`stable`, `unstable/beta`, `unstable/alpha`), até duas por pasta, e `bin/current` aponta a ativa, trocado por rename atômico. O launcher fixo `bin/bcct` (`bcct.cmd` no Windows) é o caminho absoluto que a statusline e a linha do shell gravam, e nos plugins o `${CLAUDE_PLUGIN_ROOT}/scripts/bcct` o encontra. Binário só entra conferido pelo `plugins/telegram-hooks/checksums.txt` que o release grava (`<versão> <asset> <sha256>`): o shim do npm publica o mesmo arquivo e passa ao `bcct self-install --sha256` o hash do binário da plataforma, e o plugin o traz para o `bcct update`; o `.sha256` e a attestation ficam no Release para quem baixa à mão. Se o pacote da plataforma não veio, o shim explica qual faltou e por quê e, num terminal, oferece baixar o asset do Release conferido pelo mesmo arquivo, com resposta obrigatória; fora de um terminal só explica, e `--download-binary` baixa sem perguntar. Os 7 pacotes saem por trusted publishing, com a proveniência do npm, menos a primeira versão de cada um, posta em stage pelo login do mantenedor ([Desenvolvimento/010](../Desenvolvimento/010-primeira-versao-no-npm.md)), e os pacotes Linux não declaram `libc`. As versões de teste saem nas dist-tags `alpha`, `beta` e `next`, a estável em `latest`, e a primeira versão pública é a `0.1.0-alpha.1`; até a primeira estável, o release também aponta a `latest` para a pré-versão mais nova ([Desenvolvimento/013](../Desenvolvimento/013-latest-do-npm.md)), e o `bcct update` só conta a `latest` quando ela aponta para uma estável (`parse_dist_tags`). O `bcct update [stable|beta|alpha|<versão>]` lê as dist-tags do npm, troca a ref e os plugins pela CLI `claude plugin` e depois baixa o binário do Release, conferido pelo `checksums.txt`. O hook de SessionStart (`bcct hook session-start`) só avisa, quando a versão do `plugin.json` difere da do binário, que é preciso rodar `bcct update`. O uninstall tira só o que é nosso, o Ctrl+C oferece desfazer o que o setup já fez, o `--set` muda uma configuração sem as perguntas, e o token fica no `.env` 0600. No clone, `npm run dev:install` põe o binário da árvore no lugar para o teste.

**Porquê:** o Claude Code copia cada plugin para `~/.claude/plugins/cache/<marketplace>/<plugin>/<versão>/`: só a pasta do plugin vai junto e o caminho muda a cada versão, então nada pode depender do clone nem de caminho relativo para fora do plugin, e o launcher fixo dá à statusline e ao shell um caminho que sobrevive às atualizações. O `.sha256` ao lado do binário vem pelo mesmo caminho do arquivo e prova que ele chegou inteiro, não quem o fez; o hash que vem no shim, cujo tarball o registry do npm assina e confere, ou no plugin, que sai de uma branch que só o release move, prova as duas coisas, e o mesmo arquivo serve ao `npx` e ao `bcct update`, que baixa do Release fora do npm. A proveniência do npm liga o pacote ao repositório e ao build, mas não garante ausência de código malicioso nem é conferida na instalação: fica como evidência pública, que `npm audit signatures` confere. A doc do npm põe a falta de uma dependência opcional como responsabilidade do programa e só aceita script de instalação para compilar, então o download fica no shim, com consentimento, e não num `postinstall`. Um pacote com `libc: ["musl"]` é pulado numa máquina glibc, e o musl estático roda em qualquer Linux. Sem ref fixa, quem instala entre duas versões recebe a `main` ainda não lançada. O `current` é um arquivo, e não um symlink, porque no Windows o symlink exige privilégio ou Developer Mode. O SessionStart roda no caminho crítico de toda sessão, então não baixa nada: só avisa. O Linux em musl estático roda também no Alpine. Entre os modelos de distribuição de plugins comparados, o de shim no npm com binário por plataforma, hash no plugin e pasta por versão é o que melhor cabe num setup que pede token e pareia conta no terminal.

**Descartado:** conferir o binário pelo `.sha256` ao lado no Release: prova integridade, não autoria. Tratar a proveniência do npm como a garantia do binário: ela prova a origem do build, não o conteúdo, e a instalação não a confere. Conferir a proveniência no setup: nenhum dos plugins de referência faz e pede rede e npm 8.15+. Publicar com token, sem proveniência: perde a evidência e guarda um token. Hash em cada pacote de plataforma: viaja no mesmo tarball do binário. Só a integridade do npm: a conferência do `self-install` vira circular. Baixar sozinho, sem perguntar: baixa de fora do registry sem escolha explícita. Baixar no `postinstall`: contraria a doc de scripts e não roda com `--ignore-scripts`. `libc: ["musl"]` nos pacotes Linux: o npm os pula numa máquina glibc. Conferir a attestation dentro do binário: sigstore no binário e rede a mais. Marketplace sem ref: quem instala entre versões recebe a `main` não lançada. Sempre `#v<versão>`: o plugin nunca atualiza sozinho. A `main` apontando para a tag ou um repo de marketplace separado: três clones ou o dobro de manutenção. O SessionStart reparar ou baixar o binário, na hora ou em `async`: fica no caminho crítico da sessão. Symlink para a versão ativa: exige privilégio no Windows. glibc no Linux: não roda no Alpine. Clone e `npm run setup` para usuários: prende tudo à pasta do clone. Publicar já um pacote npm com o setup em JS: seria jogado fora com o binário. Só o marketplace, sem shim: o token e o pareamento pedem terminal, e um plugin não declara statusline nem linha do shell. `bun install` no plugin a cada versão: sem conferir hash. `userConfig` sensível para o token: no Linux vai em texto para o `.credentials.json`. Copiar os hooks para `~/.claude/hooks/`: carregaria tudo duas vezes. `curl | sh`: o `npx` já cobre.
