# 008. Cada release é anunciada em quatro canais do Telegram, sem repetir

> **Versão:** 3 · **Decidido por:** pedromondek
> **Cards:** [#12](https://github.com/pedromondek/better-claude-code-telegram/issues/12) · [#16](https://github.com/pedromondek/better-claude-code-telegram/issues/16)
> **Branches:** `0012-announce-each-release-with-its-gifs-on` · `0015-every-version-pull-request-fails-the`
> **Criado em:** 2026-11-25 18:51 · **Atualizado em:** 2026-11-26 22:39
> **Âncoras:** `.github/workflows/announce-release.yml` · `.github/workflows/release.yml` (job `announce`) · `scripts/release-announce.mjs` (`buildAnnouncements`, `newFeatures`, `postAnnouncements`, `parseNotes`) · `scripts/release.constants.mjs` (`ANNOUNCE_CHANNELS`) · `scripts/release-notes-layout.mjs` (`notesSkeleton`, `followAlert`, `legendAlert`) · `scripts/release-pr.mjs` (`pullRequestBody`) · `.claude/skills/release-notes/SKILL.md`

**Decisão:** toda versão publicada é anunciada pelo `announce-release.yml`, chamado pelo job `announce` do `release.yml` depois do `verify` ou disparado por `workflow_dispatch` numa PR de versão mergeada. Ele roda o `scripts/release-announce.mjs` sobre o `docs/releases/<x.y.z>/<stage>.md` do commit de record. São quatro canais, um por idioma e por trilha (`ANNOUNCE_CHANNELS`): `@bcct_tips` e `@bcct_tips_br` recebem só as estáveis, e `@bcct_tips_prereleases` e `@bcct_tips_prelancamentos` recebem todas. Uma pre-release vai só aos canais de pre-release. Uma estável posta o `stable.md` inteiro nos canais estáveis e, nos de pre-release, um "está estável" só com os itens ✨ que nenhuma pre-release da pasta teve (`newFeatures`). Cada versão abre com um post (resumo, link da Release e linha `npx` do dist-tag), e cada item ✨ com demo vira um `sendAnimation` em resposta a ele, com a legenda no estilo Telegram Tips sem o ✨. No GitHub o item leva o GIF; no canal vai o MP4 nítido do comentário `<!-- telegram: <url> -->` do idioma (o item pt-br pode ter o próprio; senão vale o do en-us; senão o GIF). Toda mídia é baixada antes do primeiro post, até 50 MB. O token mora só no environment `telegram-announce`, que pede aprovação, e o `release.yml` o repassa por nome; `DRY_RUN=1` manda tudo ao `TELEGRAM_TEST_CHANNEL`. O corpo da Release abre com quatro alertas do GitHub, os dois idiomas juntos: o `> [!TIP]` 📣 com os quatro canais, um `> [!IMPORTANT]` 🚀 com a instalação e outro 🔄 com a atualização (decisão [011](011-instalacao-na-release.md)) e o `> [!NOTE]` com a legenda dos emojis usados. A abertura de cada versão fica fixada no canal (decisão [012](012-fixar-a-abertura-no-telegram.md)). Depois vêm o bloco `🇺🇸 English` e o `🇧🇷 Português`, os dois recolhidos, e o item ✨ com demo leva o mesmo GIF nos dois. A PR de versão já nasce com esse esqueleto (`notesSkeleton`, chamado pelo `pullRequestBody`), com o rascunho do git-cliff no bloco en-us, e a `/release-notes` o preenche. O anúncio lê só os blocos de idioma, então os alertas não viram post.

**Porquê:** cada leitor vê só o seu idioma e cada legenda tem os 1024 caracteres inteiros; quem segue só as estáveis não recebe alpha, e quem segue as pre-releases não recebe o mesmo item duas vezes. Um canal não deixa o assinante escolher idioma nem trilha (canal não tem tópicos, e botão pediria um bot rodando e uma lista de assinantes), então a escolha é o próprio canal. O Telegram ignora o thumbnail de MP4 no `sendAnimation` (testado no canal de teste), então a capa é o primeiro quadro do vídeo. No GitHub o MP4 vira um `<video>` sem autoplay nem loop, então o GIF fica na Release. Segredo de environment que o chamador não repassa chega vazio no workflow chamado (doc do GitHub, "Reuse workflows"). Baixar a mídia no meio dos posts deixava um canal com a abertura sem a demo, e a reexecução duplicava os canais já postados. Com os dois idiomas recolhidos, o leitor abre só o seu; o pt-br sem o GIF ficava sem contexto; e a linha 📣 e a legenda no fim de cada idioma passavam despercebidas. O alerta dentro de `<details>` não renderiza (o GitHub mostra uma citação com o `[!TIP]` escrito, conferido pela API de Markdown), por isso os dois ficam fora dos blocos. A PR de versão é aberta pelo workflow pela API, então o esqueleto sai do código, não de um template do GitHub. As bandeiras ficam, mesmo virando as letras US e BR no Windows, que não tem desenho de bandeira na fonte de emoji.

**Descartado:** um canal só, com o pt-br num `expandable_blockquote` — divide os 1024 da legenda entre os idiomas e mostra os dois a todos. Dois canais, um por idioma, com todas as versões — quem só quer a estável recebe cada alpha. Escolher o idioma por botão ou thread — canal não tem tópicos, e botão exige bot rodando e guardar quem assina. `sendMediaGroup` para juntar os GIFs — não aceita animação. Capa pelo thumbnail do MP4 — o Telegram o ignora. MP4 também no GitHub — fica parado, com controles e sem loop. GIF no canal — chega recomprimido e pequeno. `secrets: inherit` no `release.yml` — entregaria também a `RELEASE_APP_PRIVATE_KEY` ao workflow chamado. O en-us aberto com só o pt-br recolhido — o inglês ocupa a Release e o pt-br fica sem a demo. O pt-br logo abaixo de cada item, com o GIF depois dos dois — mostra os dois idiomas a todos. O TIP no fim ou o alerta `IMPORTANT` — o primeiro some depois dos blocos, e o segundo indica algo que a pessoa precisa fazer. A imagem de bandeira do próprio GitHub — dentro do `<summary>` ela vira um link que abre a imagem em vez do bloco. Os sete GIFs renderizados de novo em pt-br — o mesmo GIF basta, porque o vídeo do canal pt já abre com o título em português.
