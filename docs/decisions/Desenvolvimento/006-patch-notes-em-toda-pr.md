**Decisão:** toda PR para a `main` leva na descrição a seção `## Patch notes / Notas da versão` do `.github/pull_request_template.md`. A seção tem um bloco recolhido por idioma, `<details><summary>🇺🇸 English</summary>` e `<details><summary>🇧🇷 Português</summary>`, só com o que o público nota, no formato do `/release-notes`. O `/commit` monta a seção e aprova cada parte por `AskUserQuestion`. O `check-pull-request-notes.yml` roda à parte do CI e fora do `CI passed`, no `pull_request` com os tipos `[opened, reopened, edited, synchronize]` e sem `if` no job, então roda também em fork. Ele chama o `npm run pr:patch-notes -- check <n>`, que renderiza a descrição pelo `POST /markdown` do GitHub (modo `gfm`) e olha os blocos que aparecem sob a última linha com o título da seção. As notas de cada bloco são o primeiro candidato cujo render é igual ao bloco que o GitHub mostra: o bloco sem os comentários fechados, o bloco cru, ou o cru até um `</details>` seguinte. O check falha quando o bloco falta, não aparece no GitHub (escondido por comentário HTML ou dentro de código), está vazio, ainda é o placeholder ou não se lê desse jeito. Os testes só leem renders gravados da API real pelo `npm run pr:patch-notes:record`. As branches `dependabot/`, `release/v` e `revert/` ficam isentas. O `npm run release:patch-notes` junta, pelos merge commits do primeiro pai, as PRs mergeadas na `main` desde a última tag, e é o ponto de partida do `/release-notes`. O check entra à mão na proteção da `main`.

**Porquê:** a nota escrita com a mudança fresca, já separada entre o que é público e o que fica omitido, faz das notas da versão uma reconciliação, e não uma reescrita a partir dos títulos dos commits. Uma versão junta várias PRs. A descrição comporta cerca de 65.536 caracteres, e o maior corpo medido tem uns 6,4 KB. Um job pulado conta como Success, mesmo sendo check obrigatório (doc do GitHub, "control jobs with conditions"), por isso o job não tem `if` de fork nem filtro de corpo. O próprio GitHub é o oráculo do que aparece: o corte no `<!--` aberto, medido contra o render em 31 casos, deixava passar 3, e o código cercado também esconde o bloco. A volta pelo render garante que as notas lidas são as que o leitor vê.

**Descartado:** um comentário da PR por idioma, com marcador e links na descrição — o tamanho não exige, e a descrição sozinha é mais simples para quem lê e para o `/release-notes`. Só o template, sem check — "toda PR leva as notas" ficaria sem garantia. O check como passo do `check-pull-request.yml` dentro do `CI passed` — editar só a descrição não roda o check de novo. Filtro de corpo no `edited` (rodar só quando o corpo muda) — um run pulado substitui uma falha anterior. O corte no primeiro `<!--` aberto, sem regex — deixava passar 3 casos e não via o bloco dentro de código. A regex CommonMark — deixa passar mais casos, tem tempo quadrático e é difícil de manter. Um parser CommonMark local — pode divergir do render do GitHub. O mesmo corte na descrição inteira — muda o contrato de 2 testes, já que um `<!--` em código no "How it was verified" reprovaria a PR.
