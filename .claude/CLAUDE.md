# better-claude-code-telegram

Telegram for Claude Code: a fork of the official Telegram channel plugin extended with `AskUserQuestion` buttons, a notice when Claude waits on you, voice transcription and one bot shared by every Claude Code instance on the machine. Each user runs it with a bot of their own.

**Stack:** TypeScript (strict) for the channel server and its extensions, Rust for the `bcct` binary (hooks, setup, health, launcher and status line), Node.js scripts (`.mjs`) for the npm shim, the release and the tooling, Bun to run the channel server, Vitest, Stryker, oxlint, ESLint, Prettier, Husky. One layer, no backend/frontend split.

## Layout

- `plugins/telegram/` - the channel plugin fork (`server.ts`, skills) with the project's own TypeScript in `plugins/telegram/extensions/`. Upstream files stay identical to the official plugin; see `NOTICE` for the exceptions, and keep it in step when one is added.
- `plugins/telegram-hooks/` - the hooks plugin: `hooks/hooks.json` calls the `bcct` binary through `scripts/bcct`.
- `plugins/bcct/` - the `/bcct:` skills (setup, health, token, pairing and the rest).
- `scripts/` - release, mutation, coverage, dev install and git helpers, each with its test in `scripts/__tests__/`.
- `npm/shim/` - the code of the published `@pedromondek/better-claude-code-telegram` package (its name, command and platforms in `npm/shim/shim.constants.mjs`), with its test in `npm/__tests__/`: `npx @pedromondek/better-claude-code-telegram [step | health | update [target] | uninstall [version]] [--download-binary]` takes the binary of the platform package (or, when npm left it out, downloads it from the GitHub Release after a yes, or with `--download-binary`), checks it against the `checksums.txt` it ships, runs `bcct self-install` and then the command.
- `rust/` - the Rust workspace of the `bcct` binary (`rust/crates/bcct/`), with the toolchain pinned in `rust-toolchain.toml` at the root and its lints, `clippy.toml`, `rustfmt.toml` and `deny.toml` in `rust/`.
- `.claude/` - `skills/commit`, `skills/decision` and `skills/release-notes` and `hooks/` are versioned, with the hook tests in `.claude/hooks/__tests__/`. Local and gitignored, like `.claude/rules/`: `skills/cr/`, `skills/pre-pr/`, `agents/` (`security`, `review-collector`, `review-collector-deep`, `verificador`) and `workflows/` (`cr-fanout`, `cr-consenso`, `cr-compare`, `cr-redator`, with their tests in `.claude/workflows/__tests__/`), plus the reports in `docs/cr/`.
- `.husky/` - git hooks, with their tests in `.husky/__tests__/`.
- `.github/` - `workflows/ci.yml` only orchestrates: it calls one reusable task per job (`push-checks.yml` runs the pre-push itself on Linux, without the mutation, and then, when `npm run ci:rust-other-stage` finds `rust/` in the range, the Rust tests again with the version swapped to its other stage (`release:version -- swap-stage`), since a pre-release binary warns, registers its own tag and asks before an update; `check-rust-platforms.yml` runs clippy and the Rust tests on macOS and Windows; `check-mutation.yml` is the mutation gate: a plan job lists the Rust mutants of the range (`--in-diff`, with `--iterate` over the mutants caught by earlier runs of the branch, kept in `actions/cache` and saved also on the pull request, scoped to its ref) and hands the same list to up to 20 `--shard` jobs, and Stryker runs in one job with the incremental of `main`; a range that touches a dependency, the mutation config or a test mutates from scratch, Stryker over every extension, and the manual dispatch is the full run without `--iterate` before the merge; `check-pull-request.yml` checks the title and the new dependencies; `audit-workflows.yml` runs zizmor and pinact online on the head and on the merge-base of the range when it changes a workflow or its lint config, and fails only on a finding the range brings, while `report-workflow-audit.yml` opens or comments the issue labeled `ci/online-audit` when it fails on main) and closes with the `CI passed` aggregate check, red when a task failed or was cancelled and when `npm run ci:passed` finds a finished job of the run, inside a task too, that failed, was cancelled or timed out (a job GitHub cancelled because no hosted runner took it, with no step and the "not acquired by Runner" annotation, only leaves a warning), and each task can also be dispatched or re-run on its own; `audit-workflows-on-schedule.yml` audits the whole of main every Monday, since the advisories change without a commit, and reports a failure the same way; `prepare-release.yml` (dispatched by hand) plans the next version, waits in the `release-approval` environment when a minor or major needs approval, and opens the version pull request with the release app token, whose key only the `release` environment holds; `release-pull-request.yml` runs apart from the CI, on every push and every edit of a `release/v*` description, and keeps it red until the notes replace the git-cliff draft and while its version is not free and in order; `check-pull-request-notes.yml` also runs apart from the CI and outside `CI passed`, when a pull request to main opens, reopens, is edited or gets a push, and by hand, and keeps it red with `npm run pr:patch-notes` while its English or Portuguese patch notes block is missing, not shown by GitHub, empty, still the template placeholder or unreadable, except on a `dependabot/`, `release/v` or `revert/` branch; `release.yml` runs on each push to `main` (or by hand on a merged version pull request), since the `release` and `telegram-announce` environments accept only `main` and a `pull_request` run has `refs/pull/N/merge` as its ref, and goes on only for the merge commit of a version pull request merged with the default subject (`Merge pull request #N from <owner>/release/v<version>`), which the push gate and `npm run merged-pr` both read (`merged-pr` finds the merge in the history of `main` and takes the branch from that subject); it publishes the version with `npm run release:publish`: it builds and attests the binaries at the merge, commits the checksums and the notes with the release app token from the `release` environment, and publishes the immutable Release at that commit, then stages the npm packages through trusted publishing for the maintainer to approve, and waits in the `npm-approved` environment until the maintainer, having approved them on npmjs.com, approves the run too, since npm sends no event of it; then `verify-release.yml` (called by the release, or dispatched alone on a merged version pull request) checks the Release and the npm packages with `npm run release:verify`, and a stable version then moves the `stable` branch, the marketplace ref the setup registers, forward to the verified commit; `announce-release.yml` (called by the release after the verify, which passes it the bot token by name, or dispatched alone on a merged version pull request, refused while npm does not serve that exact version) finds the version and its record commit with `npm run release:verify -- record` and, from the `telegram-announce` environment, which alone holds the bot token, posts the notes of that commit on the Telegram channels with `npm run release:announce`; `build-binaries.yml` (called by the release, or dispatched alone without publishing) builds the 6 native binaries, each on its own runner, checks each one with `npm run release:binary`, attests it with `actions/attest` only when the release passes `attest: true`, and uploads it with its sha256 as an artifact; `lock-pull-requests.yml` runs apart from the CI and, with `npm run pr:lock`, locks the conversation of every pull request of the repository once the `CodeRabbit` check of its head completes (CodeRabbit skips a push that reaches a locked conversation, so the pre-push of the developer unlocks the pull request of the pushed branch with `npm run pr:unlock`; on open, reopen and each push the job waits up to 20 minutes for the CodeRabbit check of the head and locks, also after the wait or an error, with a last step that locks with `pr:lock -- --lock-only` when the job is cancelled or fails, unless a newer push moved the head, whose run locks it, and when the push arrived locked before CodeRabbit finished it warns that a person can unlock it and comment `@coderabbitai review`, and keeps it locked; by hand, it locks every open one, and with `PR_NUMBER` and `--lock-only` just that one), so only who has write access comments, while Settings restricts opening pull requests to collaborators; `watch-upstream.yml` runs every 3 days (and by hand) `npm run upstream:watch`, which opens an issue labeled `upstream` when the official plugin leaves the version this copy came from (`scripts/upstream.constants.mjs`, tied to `NOTICE` by a test), or comments the open one when it moves again; `manage-ci-cache.yml` deletes the caches of a closed pull request and, every Monday, calls the checks, the Rust and the mutation tasks on `main`, so its caches are not evicted after 7 days unused; every cache saves only on `main` (`mise-action` with `cache_save`), except the caught mutants above; `dependabot.yml` opens only security updates (version updates are off), and a Dependabot rule in the repository settings limits them to high and critical alerts, with one exception: the major versions of grammy in `plugins/telegram`, 30 days after they come out; since Dependabot makes no security update for bun, `audit-plugin-dependencies.yml` runs `npm run audit:plugin:issue` every Monday (and by hand), which opens or comments the issue labeled `security` while a dependency of the plugin has a high or critical advisory. `ISSUE_TEMPLATE/` holds the Bug report, Feature request and Task forms, each in English and in pt-br (`1-bug.yml` and `1-bug.pt-br.yml`, with the same fields, held together by a parity test), with no blank issue and the private vulnerability report as the only link, and `pull_request_template.md` is one template in both languages, ending in the patch notes, one collapsed block per language. `.github/__tests__/` mirrors each of them with a test (`layout.test.mjs` requires the mirror).
- `docs/` - `docs/setup/` (setup guide) and `docs/decisions/<Scope>/NNN-slug.md` (one file per decision, `000` is the scope index).

## Main scripts

- `bcct setup` (`npx @pedromondek/better-claude-code-telegram`, or `bcct setup <step>`) - interactive setup; `bcct health` checks it and `bcct uninstall` undoes it. In a clone, `npm run dev:install` puts the binary of the working tree in place to run them.
- `npm run dev:binary`, `dev:plugins`, `dev:install` - the local install for a live test (`scripts/dev-install.mjs`): `dev:binary` builds the release binary (under `systemd-run --user` with `MemoryMax` from `BCCT_BUILD_MEMORY`, 5G by default, and `CARGO_BUILD_JOBS` 3 by default, when it can start a user unit; directly otherwise; respecting `CARGO_TARGET_DIR`) and installs it with `bcct self-install`; `dev:plugins` reinstalls the plugins of the marketplace, since the same version never refreshes the plugin cache, and turns `telegram@` off again, since only `claude --telegram` turns it on; `dev:install` runs both, the plugins only after the binary succeeds.
- `npm test` - unit suite; `npm run test:e2e` - end-to-end suite; `npm run test:all` - both; `npm run test:hooks` - the hook tests; `npm run test:workflows` - the tests of the local `/cr` workflows in `.claude/workflows/__tests__`, which warns and skips (exit 0) in a clone without that folder.
- `npm run lint` - oxlint, ESLint and `tsc`; `npm run lint:typos`, `lint:secrets`, `lint:lockfile`.
- `npm run lint:workflows` - runs `lint:workflows:actionlint`, `:jactionlint` (only the checks of the calls between workflows and of a pipeline without `pipefail`), `:zizmor` (offline, with every audit of the auditor persona; exceptions only in `.github/zizmor.yml`) and `:pinact` (offline) in parallel, each through the binary of `mise.lock`, and reports every failure; outside `npm run lint`, it runs in the pre-commit, the pre-push and the CI when a workflow or its lint config changes.
- `npm run audit:workflows` - the online audit of `audit-workflows.yml` (`lint:workflows:zizmor:online` and `lint:workflows:pinact:online`, with a token, which also refuses an action younger than the 7 days of `.github/pinact.yaml`, the `minimum_release_age` of `mise.toml`; an urgent security update gets a `min_age: 0` rule for that action only, removed once it turns 7 days old); `npm run audit:workflows:issue` opens or comments its issue, and only prints it with `DRY_RUN=1`.
- `npm run audit:plugin` - `bun audit` (the bun of `mise.lock`) on `plugins/telegram/bun.lock`, failing on any high or critical advisory; it runs in lint-staged when the lock of the plugin changes and in the pre-push when its lock or `package.json` changes, and `audit:plugin:issue` opens or comments the issue labeled `security`. The lock is resolved within the ranges of the upstream `package.json`, with `bun install --minimum-release-age` of 7 days, never with `bun update`, which rewrites those ranges.
- `npm run lint:plugins` - `claude plugin validate` on every plugin of the marketplace (strict except the upstream one) with a temporary config folder, so it never touches the one in use; without the `claude` CLI it warns and skips, except in CI.
- `npm run format` / `format:check` / `format:file -- <files>` - Prettier.
- `npm run test:mutation`, `test:mutation:changed`, `test:mutation:score`, `test:mutation:baseline` - Stryker.
- `npm run rust:check` (`cargo check`, short and quiet, for the edit loop), `rust:lint` (`rust:clippy`, clippy with `-D warnings`, and `rustfmt --check`), `rust:test` (nextest), `rust:cov` (100% of lines, after clearing the previous coverage build), `rust:cov:missing` (the lines the last `rust:cov` left uncovered, without building again), `rust:deny` (known vulnerabilities and yanked versions), `rust:mutation` (cargo-mutants, always `--in-place`, with the `mutants` profile of `rust/Cargo.toml`), `rust:mutation:ci` (the `plan`, `shard` and `merge` steps of `check-mutation.yml`), `rust:build` (release binary, after clearing the previous release build, which keeps no incremental cache), `rust:clean` (`cargo clean`, also after a dependency upgrade, so the old versions leave the incremental test build). The cargo tools come pinned through mise. Builds go to `rust/target` by default; set `CARGO_TARGET_DIR` to build elsewhere (the pre-push and `check:commit` respect it), and cap the memory of the job when that folder is in RAM (tmpfs).
- `npm run tools:lock` - rewrites `mise.lock` after a change in `mise.toml`; mise refuses any tool version younger than 7 days.
- `npm run release:binary -- <target> <output folder>` - checks a release binary built for one of the 6 targets of `scripts/release-binary.mjs` with the `llvm-readobj` of the pinned toolchain (the architecture; on Linux, no shared library and no dynamic loader; on Windows, no C runtime DLL) and its `--version` against the project version, then copies it under its asset name (`bcct-linux-x64`, `bcct-win32-arm64.exe`) with a `.sha256` next to it.
- `npm run release:checksums -- <assets folder>` - appends one `<version> <asset> <sha256>` line per asset of the project version to `plugins/telegram-hooks/checksums.txt` (creating it with its header), after checking each asset against its `.sha256`; it refuses a version that already has lines, since the file only grows.
- `npm run release:npm -- <assets folder> <output folder>` - builds the 7 npm packages: the shim (`npm/shim/` with the release `checksums.txt`, the platform packages as optional dependencies on the exact version, and the unscoped `better-claude-code-telegram` command) and one package per platform (`@pedromondek/better-claude-code-telegram-<linux|darwin|win32>-<x64|arm64>`, with `os` and `cpu` and no `libc`), refusing an asset that is missing or does not match `checksums.txt`.
- `npm run release:npm:publish -- stage <packages folder> | trust` - `stage` (version in `VERSION`, run by `release.yml`) runs `npm stage publish` on the 6 platform packages and then the main one, public and on the dist-tag of the stage (`alpha`, `beta`, `next`, `latest`, from `scripts/release.constants.mjs`), skipping a package that already has the version; the maintainer then approves the 7 in one batch, with one 2FA challenge, on the Staged Packages tab of npmjs.com. `trust` runs `npm trust github` on the 7 packages on the terminal, where npm asks for the one-time password of the account, so each lets only `release.yml` in the `release` environment stage it; `npm trust` needs the package to exist, so the first version of a new package is staged with the maintainer's own login and `trust` runs after it. Both need npm 11.15.0 or later.
- `npm run pr:unlock -- <branch>...` - the last step of the pre-push, only after every check passed (the mutation too, unless `PREPUSH_SKIP_MUTATION=1` skips it), and never in CI or in `check:commit` (which sets `PREPUSH_SKIP_PR_UNLOCK`): unlocks the open pull request of each pushed branch with the gh of the developer, so CodeRabbit reviews the push before `lock-pull-requests.yml` locks it again; without gh, without a login, without an open pull request or on an error of GitHub it prints one line and lets the push through.
- `npm run release:cliff` - git-cliff with `cliff.toml`: reads the commits through the emoji, gives the next version (`--bumped-version`; `feat` bumps the minor, `fix`, `perf` and `security` the patch, maintenance alone keeps the version of the last tag, and a breaking change stays on the minor while the version is 0.x) and the release notes (features, fixes, performance and security; maintenance and fixups stay out).
- `npm run release:version -- check | set <version> | next <alpha|beta|rc|stable> | swap-stage` - the one project version, kept in `rust/Cargo.toml`, `rust/Cargo.lock`, both `package.json`, `package-lock.json` and the three `plugin.json`: `check` names the file that differs, `set` writes all of them, `next` moves inside a pre-release (`alpha.1` → `alpha.2`) or forward a stage (`alpha` → `beta.1` → `rc.1` → stable) and, from a stable version, takes the base from the git-cliff bump and the stage the developer chose (`0.2.0` with a feature and `alpha` gives `0.3.0-alpha.1`, with `stable` gives `0.3.0`), and `swap-stage` writes the other stage of the current version (`0.2.0` gives `0.2.0-alpha.1`, a pre-release gives its stable base), so the tests run on a binary of each stage.
- `npm run release:pr -- plan|prepare <alpha|beta|rc|stable|version> | check-version | check-notes` - the version pull request, run by `prepare-release.yml` and `release-pull-request.yml`. Every version is checked against all that was released (the tags, the published Releases, npm, and `docs/releases` with `checksums.txt` in the repository): it must be new, come after everything by semver order and skip no number (each level goes up by one and resets the ones to its right, or the open pre-release line goes on), as `scripts/release-order.mjs` states. `plan` computes the next version (or takes the exact one), says whether it is a patch, minor or major and whether it needs approval (the version that opens a minor or major base, and the stable of that base), and writes them for the next jobs and the run summary. `prepare` checks again and commits the version files through the GitHub API to a new `release/v<version>` branch from the checked-out commit, then opens the pull request with the layout of the notes between `<!-- notes -->` and `<!-- /notes -->` (`scripts/release-notes-layout.mjs`): a `<!-- draft -->` line, the 📣 TIP, the 🚀 IMPORTANT with the install command (on the dist-tag of a pre-release, with no tag for a stable version) and the command of the exact version, the 🔄 IMPORTANT with the update commands and the legend NOTE alerts, the 🇺🇸 block holding the git-cliff draft and an empty 🇧🇷 block. `check-version` checks the version of the branch in `PR_BRANCH`, and `check-notes` the description in `PR_BODY`, which fails while the notes are the draft or empty.
- `npm run pr:patch-notes -- check <pull request number>` and `npm run release:patch-notes -- [<tag>]` - the patch notes of the pull requests (`scripts/patch-notes.mjs`), the `🇺🇸 English` and `🇧🇷 Português` blocks under `## Patch notes / Notas da versão` in the description. `check`, run by `check-pull-request-notes.yml`, reads the description and the head branch through `gh`, renders the description with GitHub's Markdown API (`POST /markdown`, `gfm`) to see which blocks show under the last heading line, takes as the notes of each block the first candidate (without its closed comments, raw, or raw up to a later `</details>`) whose own render equals the block GitHub shows, and fails naming each block that is missing, not shown by GitHub, empty, still the template placeholder or unreadable that way, except on a `dependabot/`, `release/v` or `revert/` branch. `release:patch-notes` lists the pull requests merged on main since the tag (the last one by default, the whole history without one) by the first-parent merge commits, prints the two blocks of each and names the ones without them, for `/release-notes`.
- `npm run pr:patch-notes:record` - renders every body of `scripts/__tests__/fixtures/patch-notes-bodies.mjs` (built from the pull request template) through the same Markdown API and writes each text the check asked to render, the bodies and their candidate blocks, to `scripts/__tests__/fixtures/patch-notes-renders.json`, the only renders the patch notes tests read; run it again when a body, the template or the parsing changes, since a test fails naming it when a text has no recorded render.
- `npm run release:publish -- plan | record <assets folder> | release <assets folder> | stable` - the publication of a merged version pull request (`PR_NUMBER`), run by `release.yml`. `plan` reads the pull request, refuses one that is not a merged `release/v<version>` with written notes, a version already published or out of order, and a `main` that moved past the merge for anything but the record of this version, which it resumes from. `record` appends the checksums of the 6 binaries and writes the notes to `docs/releases/<x.y.z>/<stage>.md`, then commits both on `main` over the merge through the GitHub API, after checking `main` again. `release` checks the binaries against the `checksums.txt` of that commit (a new build does not match), creates the draft Release at it with the binaries, their `.sha256` and `checksums.txt`, or reuses the draft of the version, and publishes it, as a pre-release or, for a stable version, as the latest. `stable` (`VERSION` and the verified `COMMIT`) moves the `stable` branch forward to that commit, only when the compare says it is ahead, creates the branch for the first stable version, and refuses a pre-release. `docs/releases/` stays out of prettier and typos, since it is the literal notes of the pull request.
- `npm run release:verify` - the check of a published version (`PR_NUMBER`), run by `verify-release.yml`, against the `checksums.txt` of the commit its tag points at, which must be the record of the merge: the Release is published, immutable, a pre-release only outside the stable, with exactly the binaries, their `.sha256` and `checksums.txt`, each matching that commit, and each binary passes `gh release verify-asset` and `gh attestation verify` signed by `build-binaries.yml`; on npm, each of the 7 packages has the version on the dist-tag of the stage, a tarball that matches its `dist.integrity`, the provenance of trusted publishing and the binary or `checksums.txt` of that commit, and `npm audit signatures` passes on an install for each of the 6 platforms. It reports every problem at once. `-- record` only hands over the version and that commit, and `-- public` only checks that npm serves that version of the 7 packages.
- `npm run release:announce -- [--print] [--root <folder>]` - the announcement of a published version (`VERSION`), run by `announce-release.yml`, from `docs/releases/<x.y.z>/<stage>.md` of the checked-out commit: per channel of `scripts/release.constants.mjs`, in its language, an opening with the summary, the Release link of `GH_REPO` and the `npx` line of the dist-tag, then, in reply to it, one post per ✨ item with a demo, captioned with the item and its extra paragraphs: the MP4 of the `<!-- telegram: <url> -->` comment of the item in that language, or else of the en-us item, or else its GIF, each downloaded once before the first post, up to the 50 MB Telegram takes, and uploaded. A pre-release goes to the pre-release channels; a stable version posts `stable.md` in full on the stable ones and, on the pre-release ones, only the ✨ items no pre-release of its folder had. `--print` shows every post with no token or network, `DRY_RUN=1` sends them all to `TELEGRAM_TEST_CHANNEL` under a `[@channel]` line, checked against the Telegram limits with that line, and posting needs `TELEGRAM_ANNOUNCE_TOKEN`, which never shows in the output; a 429 waits its `retry_after`, up to 3 times, and a rejection after the first post prints the `resume` input that, in a dispatch of `announce-release.yml` (`ANNOUNCE_RESUME`) for the same version and destination, posts only what is left; when the answer is lost after the request, it prints one resume for a post that shows in the channel and one for a post that does not; a cursor of another version, or of a dry run on a public run and the reverse, is refused before any post.
- `npm run check:commit` - runs the pre-push checks (without mutation) on a commit in a temporary worktree, with the `.husky` of that commit, so a step added later does not fail an older commit.
- `npm run check:private` - scans the staged changes for personal data.
- Run tools through these scripts, never `npx`.

## Non-negotiables

- Code, identifiers and commit messages in English; the user-facing messages follow the `en-us`/`pt-br` language the user picked in the setup.
- No comments in code unless explicitly requested; the names explain.
- Explicit return types on functions, and `===`/`!==` only.
- Every change comes with tests, covering the error and edge paths and not only the happy path. Write the test before the fix; for a refactor, a test that locks the current behavior before touching the source.
- Mutation testing is a gate: the pre-push hook runs Stryker on the pushed sources, and `check-mutation.yml` runs Stryker and cargo-mutants on the pull request, inside `CI passed`. A survivor on a changed line blocks, and the rest of a file may not exceed `mutation-baseline.json`. The baseline only goes down (`npm run test:mutation:baseline`); never raise it to get a push through.
- Never read, print or commit `.env` files or tokens; the bot token only enters through the setup.
- Tests never touch the real `~/.claude`, the real bot or the real `.git`: they run on a temporary home and temporary repositories (`vitest.setup.ts`). In Rust, only the `run_process` entry points read the process (`HOME`, `PATH` and the environment); the code below takes them as parameters, so a unit test builds it with a temporary home and no `PATH`, and a test that starts the binary clears the environment and passes `HOME`.
- No personal data in commits (emails, machine paths, tokens, other people's accounts): the pre-commit runs `npm run check:private`.
- Check the editor diagnostics of the files you edited before declaring the work done; use `npm run lint` at the end of a task and the targeted spec in the middle of it.
- Dependencies: install pinned versions, keep `package.json` and `package-lock.json` in the same commit, and run `npm run lint:lockfile` after changing either.
- Decisions that change how the project works go to `docs/decisions/` with the `/decision` skill.

## Project skills and hooks

- `/commit` - groups the changes by theme, validates each commit and pushes with approval; the only path to `git commit` and `git push`.
- `/pre-pr` - local, not versioned, like the rules (`.claude/skills/pre-pr/`). Reviews the whole branch before the PR: runs the checks, the `/cr` of the branch (with or without, per the argument) and `npm run test:workflows`, then hands over to `/commit`, which opens the PR. The hook `.claude/hooks/require-command.mjs` blocks `gh pr create` until `/pre-pr` has run on the branch in the session.
- `/cr` - local, not versioned (`.claude/skills/cr/`). Orchestrated code review by area with adversarial skeptics, consensus between two skeptics (up to 5 rounds) and zero false positives; the acceptance criterion comes from the issue of the PR, and the report goes to `docs/cr/<slug>/`, kept out of git. It runs on the local agents (`security`, `review-collector`, `review-collector-deep`, `verificador`) and workflows (`cr-fanout`, `cr-consenso`, `cr-compare`, `cr-redator`), also not versioned.
- `/decision` - records a technical decision in `docs/decisions/<Scope>/` as Decision, Why, Discarded, and updates the scope index.
- `/release-notes` - writes the public notes of the next release in the description of the version pull request, between `<!-- notes -->` and `<!-- /notes -->`, from the patch notes of the pull requests merged since the last tag (`npm run release:patch-notes`), reconciled with the git-cliff draft and the commits (the release workflow copies them to the Release and to `docs/releases/<major.minor.patch>/<stage>.md` on merge), with the 📣, 🚀, 🔄 and legend alerts on top and the en-us and pt-br blocks collapsed, the GIF of each ✨ item in both, and gets each part approved; the repository work stays in the omitted list.
- `.claude/hooks/` - hooks that enforce these conventions on tool calls (routing commit and push through `/commit`, the PR gate through `/pre-pr`, formatting and linting edited files, checking the lockfile after dependency commands); read them before relying on their behavior.

## Questions in skills

Applies to every skill in `.claude/skills/` that asks the developer something:

- A question with options goes through `AskUserQuestion`, with the recommendation first (`(Recommended)` in the label) and `multiSelect` when the choices do not exclude each other. Independent questions of the same moment go together in one call (up to 4); one that depends on another answer goes in a later call. A draft is approved through `AskUserQuestion` too: one question per part, its text in the `preview` and "Approve (Recommended)" first, the adjustment through "Other". Only text that does not exist yet, such as a free description the developer gives, stays in prose.
- The argument pre-answers. The developer may pass the answer in the command itself, as a keyword or in free language (`/commit stage`, `/pre-pr skip the review`). What the argument answers is not asked again: confirm in one line what was understood. An ambiguous argument falls back to the question.
- Each skill declares the answers it accepts in the `argument-hint` of its frontmatter and in an **Argument** section at the top. A skill that calls another passes along the part of the argument that belongs to the other.
- A pre-answer is valid only for that run and never replaces an approval the rules require case by case, such as each git operation outside the approved plan.

## Orchestration and models

The main session orchestrates, and each piece of work goes to the model sized for it. The current version of each family applies.

- **Opus** (main loop, `high` effort): whatever needs judgment: planning, deciding, triaging mutation survivors, designing, reviewing and integrating.
- **Sonnet** (`model: "sonnet"`, `medium` effort by default, `high` only as an exception when the task needs more reasoning): surveys (mapping files, inventories, comparing versions, reading a changelog or doc) and simple, well-specified implementation.
- **Haiku** (`model: "haiku"`, always `high` effort): trivial reading (finding a file, counting occurrences, extracting a snippet, checking a fact). It only reads and never writes a file.

What an agent returns is checked by the orchestrator before it becomes code, a commit or an answer; an agent never commits or pushes. A workflow is used only when the fan-out passes five agents.

## Local rules

The maintainer's detailed rules live in `.claude/rules/` (local, not versioned) and load by path when present. Without them, this file and the scripts above are the contract; the hooks and their tests under `.husky/__tests__/` are the source of truth for what each git hook enforces.

## Keeping the docs true

- No task IDs and no temporal wording in versioned files: state the convention as it holds, with an anchor to a rule, a file, a symbol or a lint mechanism.
- When a convention, script or behavior changes, search the docs, skills and READMEs that cite it and fix them in the same commit.
- Every doc has its own folder, `docs/<name>/<name>.md` (en-us) and `docs/<name>/<name>.pt-br.md`; decisions are written in pt-br.
